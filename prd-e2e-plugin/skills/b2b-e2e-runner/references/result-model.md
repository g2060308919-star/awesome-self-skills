# 检查点、探索与结果模型

## 权威标准

`expected[].text` 是唯一通过标准。页面显示近义词不能自行放宽；例如期望“评分”而实际只有“用户评分”，若精确语义不满足就记录未通过和实际文字。运行后的新标准只能进入新用例和新 Run。

每个 oracle 映射为 `<case_id>/<step_id>/<oracle_id>`，独立保存事实与证据状态。不得因后续阻塞覆盖已完成项。

## 固定四态

| 内部值 | 展示 | 使用条件 |
|---|---|---|
| `passed` | 通过 | 明确事实支持满足原文 |
| `failed` | 未通过 | 明确事实支持不满足原文 |
| `undetermined` | 无法确定 | 已尝试但事实不足 |
| `not_executed` | 未执行 | 整条用例在正式执行前明确排除 |

缺账号、环境/工具阻塞、没有动态样本或执行中断均不是 `not_executed`，而是 `undetermined`。`已就绪`、`待用户准备`、`明确无法提供` 是权限资源状态，不是新的产品结果。等待期间尚未执行的检查点保留 pending/null，阶段报告的 case 聚合仍为 `undetermined`；用户明确无法提供或决定本轮不再等待时，真正受影响检查点写入具体 `undetermined` 原因，不得记为产品 `failed`、`excluded` 或 `not_executed`。已发生的失败优先级不被权限原因遮盖。

聚合顺序固定：任一检查点 failed → case failed；否则任一必需检查点 undetermined → undetermined；否则全部必需检查点 passed → passed；否则若整条 case 预先排除 → not_executed；其余 → undetermined。证据、截图、代理、清理和 Run 状态独立，不能改写产品结果。

原因必须是语义化中文事实，说明期望、实际、位置和影响；不能只写错误码、`false`、`timeout` 或“与预期不符”。通过也要写观察事实。

权限准备声明只说明账号资源状态。v2 执行前核验的是实际账号、非生产环境、已登记 Target、存储上下文和必要切换，不要求被测权限行为先成功。上下文正确而业务行为不符合原 `expected[].text` 时正常记录 `failed`；错账号、环境不明或切换未完成时先修复或协作，不把上下文问题伪装成产品失败。

协作请求是进度状态，不是产品结果。开放协作覆盖的检查点保持未完成；只暂停真正依赖该事项的范围，独立工作继续。用户明确无法协助、停止部分等待或停止全轮后，只对精确影响范围按现有四态收尾，保留既有通过和失败。

v2 最终写入 `undetermined` 时，必须内联合法 `exploration_summary` 或用 `exploration_ref` 引用先前 blocker 摘要。摘要包含精确检查点、具体缺口、已知事实、真实尝试和结果；没有尝试时使用 `not_attempted_reason`；始终说明 `cannot_continue_reason`。完整字段不能自动证明探索充分，也不能绕过开放协作或未开始检查点的终结条件。

## 报告

v2 只持久化 `report.html`，不生成 `report.md` 或等价完整 Markdown。HTML 与命令返回的 `chatTableMarkdown` 由同一次快照和日志读取建立的唯一 rows/counts 模型派生；后者只供对话发送，不落盘。历史 v1 报告对只在兼容分支生成。渲染器不重新判定或补造事实；缺失信息显示“未记录”。

HTML 固定六部分：标题、概览、测试环境、需求覆盖与验收、测试数据与清理、结论边界和后续行动。概览按全部输入用例计算四态、通过率、失败率和扣除全局用户等待后的执行耗时；时间事实不足显示“无法准确计算”。阶段报告醒目标明未完成、记录截止和待协作事项，pending 检查点仍是待继续状态。

总表每页最多 20 条；短编号只按不可变输入顺序生成并用于展示。查看弹窗保留原始 case ID、原用例/预期、对应权限、真实执行记录、结果原因、探索事实和全部关联关键截图。未记录动作不能复制原步骤后冒充实际执行。长 ID、长中文和图片不能遮挡关闭操作；固定脚本只负责分页、打开/关闭和焦点恢复。

HTML 主阅读层只展示语义化内容。关键执行记录转换为中文时间线，代理、清理、一致性和证据转换为“项目、实际情况、结论”；不得把事件对象、内部事件名、机器枚举、布尔值、空值或 JSON 代码块直接输出到 HTML。原始序号、哈希、Target ID 和完整载荷继续保存在 `execution-log.json`，HTML 只保留用例 ID、Run ID 和业务记录 ID 等理解、定位结果所必需的标识。无法生成语义摘要的记录显示统一的未识别说明，不泄漏原始载荷。

总表表头精确为：

```text
ID | 模块 | 测试场景 | 测试结果 | 成功/失败的原因
```

每条输入用例按原始顺序恰好出现一次，使用与 HTML 一致的展示短编号和四种中文结果；详情保留原始 case ID。不得增加原因分类列。截图失败只能写在证据状态/原因中，不能改变已有产品判断。

## 对话交付

最终对话中的四态统计和五列表格必须使用已校验 v2 `report` 命令返回的 `counts` 与 `chatTableMarkdown`，不得依据记忆重新汇总或判定。对话表头、展示 ID、模块、场景、结果、原因和顺序与 HTML 共享模型完全一致；每条输入用例恰好一行，即使用例很多也不能省略通过项。报告链接不能替代对话内全量表格。报告生成或一致性校验失败时，不得宣称 Run 完成或拼造表格。

最终顺序为：Run 根目录和四态数量；完整五列表格；未通过、无法确定与关键截图缺口；代理验证与自动清理结果（未使用时写“本次未使用代理”）；单一 `report.html` 链接和一致性结果。v2 CLI 的 `reportPath` 和 `htmlReportPath` 均指向 `report.html`，`reportFormat` 固定为 `html-only-v1`。密码及其他认证秘密不得出现在最终回复。
