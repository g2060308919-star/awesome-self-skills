# generate-test-cases 编译器可靠性整改 Spec

本文规定此次整改的强制行为、禁止事项和验收条件。背景见 [01-context.md](01-context.md)，实现设计见 [02-technical-design.md](02-technical-design.md)。三份文档为同一次整改的完整交接包；不依赖历史聊天或原电脑路径。

## 1. 术语与判定规则

- **必须 / 不得**：强制约束。
- **合法输入**：处于本技能声明范围，来源和业务依据满足当前协议，结构及必要授权完整的输入。
- **任务修订**：同一运行内依原机制接受的语义修正或业务回答；不是技能版本。来源原始字节、新权威来源或实质范围变化仍触发既有新运行机制。
- **阶段上下文**：由编译器提供、供 Agent 编写用例的只读结果及引用，不是第五个语义工件。
- **构造成功**：内存候选通过构造入口检查；不等于 Runner 接受。
- **正式完成**：通过原有质量与复核流程，发布当前 manifest，并通过正式交付验证。

本 spec 不承诺软件永无缺陷。验收要求正常输入稳定完成、规定的错误被正确处理、失败可定位恢复，以及所有已知范围内的回归通过。不能通过降低检查标准实现“没有报错”。

文档未授权删除或改写现有业务语义。实现中的新发现如与核心约束冲突，必须报告；不能自行扩展任务为完整架构重写。

## 2. 需求条款

### REQ-01 保持架构与工作流

必须保留四个语义工件、现有业务澄清时机、证据和范围模型、独立复核、提交机制及正式交付机制。不得增加第五个 Agent 编写的语义工件或额外用户审批阶段。

测试用例文档生成不得要求提供执行环境、账号或执行能力证明。不得启动 E2E 或生产操作。既有 `execution_plan` 仅受共享契约回归保护，不在本次扩展范围。

### REQ-02 用例编写上下文完整可获得

当已接受的来源、证据和行为设计满足前置要求时，Runner 必须在要求编写 `case_drafts` 的回复中提供技术方案第 4 节定义的完整 `case_context`。

调用方不提交任何用例，也能通过公开流程获得所需测试点；不得要求访问私有函数、复刻哈希算法或先提交伪造用例。支持观察、模块归属、结果依据与顺序引用必须可解析。

### REQ-03 编译结果身份保持一致

上下文与最终编译必须复用同一结果及顺序计算实现。不得修改现有 OUT、TP、OBS、FLOW、ACTION、DEP 和正式 CASE 的语义身份算法。

对于同一组已接受输入，多次请求上下文的规范内容与摘要一致。输入中的非语义机器路径、当前时间、随机数不得进入这些既有语义身份计算。不同运行可有不同运行绑定和上下文摘要。

### REQ-04 正确处理阶段失败

行为设计校验或上下文计算失败时，不得接受错误工件或返回有效用例上下文。不得只处理 `need_revision` 而忽略其他实际失败状态。

必须保留最终用例阶段的覆盖、风险、语义状态和独立复核检查。提前计算上下文不构成正式用例或覆盖通过。

### REQ-05 防止失效或跨运行引用

候选 `case_drafts` 必须携带构造入口复制的 `case_context_digest`，不得加入正式 CASE 的身份投影。正式 Runner 在提交锁内复核上下文与当前已接受依据。

旧依据、错误运行、摘要不一致的候选必须被拒绝；不提交、不变更既有决定、不发布结果。恢复必须提供当前有效依据，不能简单替换摘要而忽略业务内容是否失效。

helper 必须与只读重算的当前上下文比较，篡改后重新计算摘要也不能通过。Runner 对结构合法但上下文摘要失配的候选使用 `need_revision / case_drafts / CASE_CONTEXT_STALE`；摘要缺失、格式错误、普通修订错误和引用错误各沿用相应原诊断，不混为过期。前置依据无效时先返回其实际阶段。错误码新增不改变既有顶层状态机。

### REQ-06 统一机械数据构造

必须提供技术方案第 5 节的 `prepareStageArtifact(runDirectory, validatedReply, semanticInput)` 公开入口，覆盖现有四阶段的候选构造与共享结构检查。

该异步入口用于技术方案明确的阶段写入/修正请求，必须只读当前运行、不自动提交，不替代材料恢复或业务回答等受控动作。成功结果为 `{status:"prepared", stage, artifact}`，失败为 `{status:"invalid", diagnostics}`。不得把 helper 的状态混入 Runner 状态枚举。

机械头部和当前上下文绑定由程序填写。候选 `case_id` 仍是 Agent 提供的局部标识，helper 检查非空和唯一性；正式 CASE 身份由原语义编译算法计算。不得增加另一套正式编号算法、把局部编号当作正式身份或重编号已接受历史。

调用方不得覆盖技术方案列明的程序字段；失败诊断必须可定位且不能夹带半成品。来源、动作和独立复核继续使用现有受控构造入口。证据拆分、条件组合、预期、优先级与语义局部标识仍由 Agent 提供并接受检查，不交给程序猜测。

### REQ-07 构造与校验共用契约

构造入口、Runner、外置 Schema、嵌入 Schema 与技能示例必须一致。不得通过忽略未知字段、忽略不认识的状态或静默丢弃业务内容使候选“合法”。

Schema 新增与修改必须同步正式注册和构建摘要。实际发布包必须通过公开入口验收，不能只运行源码层测试。

### REQ-08 仅维护当前技能协议

必须移除历史技能格式适配、多版本运行分派、技能升级/降级及迁移路径，不再要求用户选择版本、升级运行或处理兼容问题。

不符合当前协议的输入明确拒绝；不自动转换、不新建升级运行。没有要求支持所有历史运行。历史文件不得为此次清理而删除或改写。

仅因包含 `version`、`revision` 或 `V4` 字样，不得删除以下内容：当前任务修订、问题目标绑定、证据/复核摘要、外部 provider 契约、构建完整性及现有下游必需元数据。仍需固定字段时，由程序填当前常量，不出现版本选择逻辑。

### REQ-09 恢复与幂等

在当前单一协议内，必须保留已接受来源、用户决定和检查点。同一动作或同一已记录事务的重试不得产生重复决定、重复接受或旧结果覆盖新结果；不把用户明确发起的不同运行混同为一次重试。

候选失败不改变已接受前缀；修正已接受语义仍按原受控修订机制处理。来源字节/实质范围变化及取消后的继续，分别沿用原关联新运行机制，不向旧运行强行追加。合法复用的材料不能仅因流程重试被要求重新获取；确实失效或未获取的材料仍须验证。

并发提交依赖既有锁和摘要机制。遇到旧候选、半写入或完整性失败必须拒绝或按既有事务恢复，不最后写入覆盖。

保留 Agent/Adapter 层原有无进展重试限制：同一阶段和根因允许三次修正，第四次相同无进展结果为 `PIPELINE_NO_PROGRESS`，不新增 Runner 状态或全局计数服务。不得通过反复新建运行或行政修订绕过限制。

### REQ-10 错误分类与可理解诊断

沿用既有顶层状态。正常阶段工件请求保留 `need_revision / STAGE_ARTIFACT_REQUIRED`，不作为故障；结构/引用错误不是业务问题；业务未知不是程序异常；材料不可用不是默认允许省略材料。

Runner 的失败回复必须说明出错阶段/字段或资源、原因、提交情况及可用恢复信息；无法安全恢复时明确说明。构造 helper 的失败使用其非空 diagnostics 契约，不伪装成 Runner 回复。工具错误不得要求用户重新确认已接受业务规则。

自动修复限于确定性的机械数据。不允许自动猜预期、删除用例、升级证据等级、伪造用户或 reviewer 权威。无合法自动恢复路径时明确停止并保留现场，不能伪装成正式完成。

### REQ-11 来源与用户决定真实性

必须保持来源定位、审阅分类、签名信息处理及授权决定的原约束。只有已接受的当前目标回答才能改变对应规则；未回答部分仍保留。短确认不能借用到无关问题。

原始内容、图片参考、示例、产品规则和获取状态必须区分。机器上的缓存、来源 URL 或技术获取记录本身不能证明业务内容已读或已确认。

### REQ-12 业务质量与证据等级

Grounded 用例的预期必须有有效来源或合法推导；不得把 E1 临时输入提升为最终规则，不得用模型常识填补必要未知。保留原有 Grounded、Conditional、Blocked 语义及交付规则，不能借本次整改禁止原本合法的 Conditional 场景，也不能使其绕过关键缺口门禁。

必须检查主流程、源材料涉及的角色/状态/输入边界/异常等责任；不机械扩展 PRD 未涉及的场景。独立失败的枚举或条件结果分别可判定。

必要字段前提、角色与状态交集、AND/OR、例外和同一业务对象连续性不得丢失。步骤与预期必须对应；精确文案要求不得变成宽松近似匹配。

### REQ-13 双向覆盖与合理计数

既要从有效来源查找对应设计/用例或真实缺口处置，也要从用例断言追溯到来源。不得仅检查“已生成测试点是否都有用例”。

没有提取出的源规则，必须在来源优先的独立复核中有机会被发现。不得把探索项或无依据的“不适用”计为正式覆盖，不得为提高覆盖率删除未覆盖测试点。

不以固定用例数量验收。相同终点的单点用例与完整路径可共存；不能仅按标题或终点重复去重。

### REQ-14 独立复核保持有效

必须保持真正独立上下文、先读来源建立目标、后看生成内容的流程。生成者自检不能冒充独立复核。

首次用例候选仍须提供现有 Schema 要求的 pending 复核数据、真实身份及来源优先目标，不能省略结构或提前编造 completed 结论。业务内容、条件、前提、步骤、预期或设计责任发生变化时，旧复核结果必须失效并重新签发/执行复核。程序可以构造绑定，但不能替 reviewer 写“通过”。

测试夹具中的复核模拟仅验证协议，不是实际文档的独立审阅。本地综合样本的完整生成验收必须有真实独立复核，可使用独立 Codex 会话，不要求特定 MCP 或插件。

### REQ-15 正式交付一致性

正式发布继续以 `output/current.json` 为权威。发布前必须通过原有门禁和文件摘要校验，输出均从同一规范结果投影。

HTML、CSV、Markdown、JSON、完整会话表格和来源阅读记录不能各自维护一套业务内容。来源阅读记录仍根据技术采集事实生成，不得从用例覆盖率推断来源完整性。

不得用手写文件作为失败流程的正式替代交付。旧 ready 文件不能覆盖更新后的非 ready 状态。结果类型与“未执行测试”的含义保持原约定。

### REQ-16 可独立复现的验收

从提供的源码实施，使用文档内置材料验收，不依赖外部 MCP、原 PRD 或原运行数据。

使用背景文档的便携合成需求及受控变体建立测试夹具，通过真实构造和 Runner 入口生成数据。不能只复制一个旧成功工件测试解析。

使用背景文档第 8.2 节的完整本地综合需求验收真实生成流程，完成独立复核和正式交付校验。外部来源接口通过本地测试替身验证契约和故障处理，不修改生产校验逻辑，不声称测试替身证明了真实服务可用。原业务 PRD 回归不属于此次完成条件。

## 3. 验收测试矩阵

每项测试须记录输入夹具、实际调用入口、断言、实际结果和必要的产物引用。以下是行为要求；测试文件名与命令应映射到接收仓库真实实现。涉及现有质量、取消、材料和执行计划机制的项目是回归保护，不授权扩展这些功能或重写已经正确的模块。

| 编号 | 场景 | 必须观察到的结果 | 条款 |
|---|---|---|---|
| AT-01 | 最小合法材料推进到用例阶段，尚未提交用例 | 不依赖假空用例；回复含完整上下文；经 fact_modules 唯一追溯结果所属模块与事实 | REQ-02、REQ-03 |
| AT-02 | 同一已接受前缀重复请求、重启恢复及等待独立复核 | 规范上下文、摘要和既有语义 ID 一致；无额外提交；只更新复核记录不改变上下文摘要 | REQ-03、REQ-09 |
| AT-03 | 上下文与最终编译结果对照 | 测试点、结果、观察和顺序身份一致，无两套计算；正式 CASE 仍调用原算法 | REQ-03 |
| AT-04 | 非法行为证据或设计责任缺失 | 不接受行为候选；不返回有效用例上下文；具体错误保留 | REQ-04 |
| AT-05 | 受控触发内部编译失败或未知返回状态 | 不吞错、不前进、不发布；诊断定位故障阶段 | REQ-04、REQ-10 |
| AT-06 | 合法修正上游后，候选修订号已更新但仍携带旧上下文摘要 | `CASE_CONTEXT_STALE`；接受前缀不被错误候选改变 | REQ-05 |
| AT-07 | 修改上下文、篡改后重算摘要或跨运行引用 | helper 与当前上下文比对后拒绝；携带伪造或跨运行摘要的候选也被 Runner 拒绝 | REQ-05 |

| AT-11 | 构造完成后、Runner 提交前上游状态变化 | Runner 在锁内重新验证并拒绝失效候选 | REQ-05、REQ-09 |
| AT-12 | 外置 Schema、嵌入定义、注册清单或摘要被单独改坏 | 构建/完整性验收失败；不能带不一致产物发布 | REQ-07 |
| AT-13 | 当前完整正常生成路径 | 按现有工作流完成，无新增版本选择或人工技术审批 | REQ-01、REQ-08 |
| AT-14 | 给定明确不符合当前结构的历史协议输入 | 明确拒绝；不转换、不升级、不创建迁移运行；原文件不变 | REQ-08 |
| AT-15 | 追加澄清、材料获取、来源/范围变化、取消及继续 | 修订与关联新运行各按原机制处理；取消日志不再追加；不受兼容清理或新 helper 破坏 | REQ-08、REQ-09、REQ-11 |
| AT-16 | 写候选后中断、事务边界中断、重复恢复 | 恢复到合法状态，无半提交、重复决定或丢失已接受回答 | REQ-09 |
| AT-17 | 并发候选及较旧结果延迟写入 | 锁和依据检查有效，不出现旧结果覆盖新状态 | REQ-09、REQ-15 |
| AT-18 | 来源材料缺失与合法缓存材料重试 | 真缺失走材料恢复；合法可复用材料不无故重新索取 | REQ-09、REQ-10、REQ-11 |
| AT-19 | 部分业务回答、旧目标回答、重复有效回答 | 精确接受当前已答部分；未答保留；旧目标不误应用；重复不重复追加 | REQ-09、REQ-11 |
| AT-20 | 删除样本中的失败处理规则 | 进入必要业务澄清；不自动填默认恢复行为 | REQ-10、REQ-12 |
| AT-21 | 故意断开 Claim/Fact/点/用例引用或步骤关联 | 相应结构/引用门禁拒绝并定位 | REQ-12、REQ-13 |
| AT-22 | 固定样本故意改错预期、角色、状态或边界 | 对应来源对照/独立复核发现具体错误；结构通过不能等于业务通过 | REQ-12、REQ-14 |
| AT-23 | 从事实提取开始故意漏掉一条源规则 | 独立来源清单发现遗漏；不能只凭生成点覆盖全满通过 | REQ-13、REQ-14 |
| AT-24 | E1 等试图绕过关键缺口，并对照原本合法的 Conditional 场景 | 关键缺口仍阻断；E1 不升级；合法 Conditional 的原语义与交付处理保持 | REQ-11、REQ-12 |
| AT-25 | 伪造不适用、把探索项算正式覆盖、删除未覆盖点 | 对应证据/覆盖门禁拒绝；计数不被抬高 | REQ-13 |
| AT-26 | 同一记录完整流程与其局部单点同时存在 | 必要两类场景均保留；流程不换对象、不遗漏关键动作 | REQ-12、REQ-13 |
| AT-27 | 缺少真实独立复核，或复核后改变步骤/预期 | 不能正式发布；内容变动要求重新复核 | REQ-14 |

AT-20、AT-22、AT-23 涉及需求理解的部分，必须通过 Agent 辅助的生成验收或独立语义审阅验证；这不是启动浏览器 E2E。固定样本可使用独立编写的预期清单辅助自动断言；对一般自然语言语义，不要求纯结构校验自行理解。验收证据必须指出是哪一道检查发现了错误，不能只写“被拦截”。若只注入了一个预设拒绝结果，该测试只能证明拒绝处理协议，不能证明真实发现了语义错误。
