# generate-test-cases 编译器可靠性整改背景

本文说明需要解决的问题、现有架构、整改边界和跨机器交接条件。接收者无需阅读任何历史对话。本文是背景材料；实现设计见同目录 [02-technical-design.md](02-technical-design.md)，强制要求和验收见 [03-spec.md](03-spec.md)。三份文档作为一个包使用。

从提供的源码实施，使用本文内置的本地材料验收，不依赖外部 MCP 或原 PRD。

## 1. 任务与结论

整改对象是 `generate-test-cases` 技能及其确定性编译器。该技能把 PRD 等需求材料转为有依据、可追溯、可执行的人工功能测试用例。

目标有且只有三项：

1. 保持用例质量：预期有依据，关键规则有覆盖，条件与步骤可执行，独立复核真实有效。
2. 保持现有工作流，使合法输入能够完成生成，不被内部编号、格式或阶段接口缺失阻塞。
3. 仅维护当前一套技能协议，删除旧格式兼容、技能版本升级与迁移逻辑。

采用的技术方向是**保留编译器，在现有架构内修复接口、提供机械数据构造入口、整理错误恢复、补齐回归测试**。不删除编译器，不改成模型直接写正式文件，不新增业务工作流。

“流程不能出错”在本任务中的可验收含义是：支持范围内的合法输入必须跑通；错误输入、业务缺口及外部资源不可用必须正确分类并给出合法恢复动作；无法恢复时明确停止并保留现场，不崩溃、不死循环、不丢失已接受内容、不把失败包装成成功。它不意味着取消所有报错，也不承诺外部服务永不故障。

## 2. 当前核心架构

### 2.1 用户可见工作流

读取 PRD → 需求分析 → 必要业务澄清 → 用例设计 → 独立复核 → 导出。

已知业务缺口在设计前澄清；设计中真正新发现的缺口允许通过现有设计后澄清机制处理。不得把所有问题推迟到执行测试时。上述两处澄清属于现有机制，不增加固定问答轮数或常规二次审批。

### 2.2 四个语义工件

| 工件 | 职责 | 不应承担的职责 |
|---|---|---|
| `source_pack` | 规范化来源、精确定位、材料审阅、已接受用户决定及相关事件 | 编造业务规则 |
| `evidence_claims` | 原子事实、证据、范围与语义缺口 | 证明现实环境能执行测试 |
| `behavior_views` | 条件、状态、角色、输入域、流程等行为设计和设计责任记录 | 代替最终用例或扩展范围 |
| `case_drafts` | 业务前提、数据、步骤、步骤关联预期、独立复核记录 | 自行创造编译器管理的测试点 |

Agent 负责业务理解与语义内容；编译器负责确定性校验、规范身份、测试点计算、覆盖核算、顺序、提交与导出。程序只能规范化或绑定已有语义，不能替 Agent 作出产品决定。

### 2.3 必须保持的交付与执行边界

- `case_document` 表示人工用例文档，不要求先提供测试环境、账号、数据查询工具。
- `execution_plan` 是已有的独立下游分支，只有用户明确要求时才建立。此次不扩展或重新设计该分支。
- 正式结果以 `output/current.json` 引用并校验的规范结果为准；JSON、HTML、CSV、Markdown、完整表格及来源阅读记录保持一致。
- 本技能不自动执行 E2E、接口测试或生产操作。
- 未通过校验的候选内容不等于已接受内容；未完成独立复核不等于质量合格。

## 3. 已核实的问题与证据边界

本次只读核查日期为 2026-10-28。观察到的安装包标识为 schema `4.3.3`、compiler `0.8.3`。这两个数字只用于识别被检查的材料，不构成需要支持的版本矩阵，也不要求实施者升级版本号。

### 3.1 确认存在的阶段接口缺口

1. `case-drafts.schema.json` 的当前用例结构要求 `primary_test_point_id`。
2. `compileBusinessOutcomesV4` 在内部生成 `outcomes`、`formal_test_points`、`supporting_observations` 等结果。
3. 当前 `behavior_views` 路径通过构造空 `case_drafts` 调用完整编译逻辑进行探测；它没有把计算出的测试点作为下一阶段的输入上下文返回。
4. `artifactRequest` 在要求提交 `case_drafts` 时，仅返回阶段、Schema、修订和恢复信息，没有测试点绑定。
5. 检查到的公开导出中没有提供读取此用例编写上下文的入口；当前运行的已接受及派生工件也没有测试点编号。

因此，正常使用公开接口的 Agent 无法获得编写用例所需的编译器身份。复制内部哈希算法、自算编号或导入私有函数均不属于本方案。

这是由代码、Schema 和当时运行现场共同支持的缺陷定位。它尚不等于已经建立了自动化故障复现测试；建立该测试是实施的第一步。

### 3.2 不能把所有拒绝都归咎于编译器

过程中还出现过证据引用不符合规范分类、事实所属模块不匹配、派生结论不符合来源约束、设计计划标记不符合规则等问题。这些至少包含生成端的输入构造错误；不能通过删除相应质量检查来统一“修好”。

需要分别处理：

- 真正的工具缺陷：缺少必需的阶段输出、无法使用的恢复路径、错误吞没等。
- 可修正的候选数据错误：结构、引用、字段归属等，应定位到具体工件和字段。
- 必须由业务决定的问题：需求矛盾或必要预期未知，保留现有澄清入口。

### 3.3 缺陷的业务影响

该问题在配置管理类 PRD 的用例生成中暴露：来源、澄清与行为设计已有有效输入，但编写用例时无法从公开流程获得必需测试点。整改需要恢复这条阶段交接，而不是重新确认产品规则或绕过引用校验。

原业务材料不属于交接依赖。本文第 8 节提供独立的本地回归来源；接收者无需取得原 PRD、原型图或聊天记录。

## 4. 不改变的核心保障

1. 来源的有效性、精确定位和内容绑定；材料获取状态与业务权威分离。
2. E3 为有效来源或已授权最终规则；E2 为允许的可重放推导；E1 为明确临时假设或未声明性质的回答；不把模型常识作为产品依据。
3. 不同角色、状态、独立条件分支应独立可判定；角色与状态交集不能被误解成任一条件满足即可。
4. 覆盖已提取测试点之外，还要独立从 PRD 检查遗漏。模型漏掉一条需求时，测试点覆盖统计本身不能发现全部问题。
5. 关键语义缺口不能靠暂缓、未知、要求交付或普通继续指令绕过。
6. 独立复核使用独立上下文，先根据来源建立检查目标，再查看生成内容。内容变化后不能沿用失效的复核结果。
7. 一条用例保持一个主要业务结果，预期关联具体步骤；同一对象完整流程和必要单点场景均保留。
8. 提交、恢复、证据完整性及正式结果发布规则不弱化。不得修改已接受历史来掩盖失败。

## 5. “不考虑版本”与“保留任务记录”的界线

本次删除技能对旧协议的运行分支、旧格式适配、版本升级引导和跨版本迁移能力。不增加新的版本兼容矩阵。

以下内容不是应删除的技能版本兼容：

- 同一运行内合法语义修正或业务回答形成的 `source_revision`、决定追加记录和当前已接受检查点；
- 防止旧回答套用到新问题的目标绑定、内容摘要与复核失效检查；
- 外部来源提供方的签名清理规则及其契约标识；
- 构建清单和内容摘要的完整性校验；
- 现有下游交付引用要求的固定元数据。

仅因字段或函数名含有 `version`、`revision`、`V4` 等字样，不应批量删除或重命名。若当前协议必须携带固定格式标识，由程序填写一个当前值，不进行版本选择、升级、降级或兼容分派。

来源原始字节变化、新增权威来源或实质范围变化，仍走现有 `NEW_RUN_REQUIRED` 和关联新运行机制，不混同于同一运行的工件修正。取消后的继续仍走现有 `resume_cancelled` 新运行，不向已取消日志追加。

不要求新实现读取、转换或恢复所有历史协议的运行目录。历史数据原样保留。当前单一协议内的合法任务恢复必须可用；遇到不满足当前结构的材料，应明确拒绝，不自动建立迁移分支。

## 6. 范围与非目标

### 本次范围

- 补齐用例编写阶段的编译器输出。
- 统一阶段数据构造、引用绑定和结构校验入口。
- 同步运行代码、Schema、构建清单及技能说明。
- 清理技能多版本运行与迁移逻辑。
- 修复上述路径涉及的错误分类、恢复和幂等行为。
- 建立流程、质量门禁及交付一致性回归测试。

### 明确非目标

- 重写整个编译器，改变四工件模型、证据等级、测试点含义或身份算法。
- 增加第五个 Agent 编写的语义工件、新业务阶段、数据库、云服务或工作台 UI。
- 放松质量门禁、减少必要业务澄清、自动补全产品规则。
- 新建自动 E2E 执行能力、修改 Cooper、改变业务 PRD。
- 重构其他技能或重新设计 `execution_plan`；共享接口仅做必要的回归保护。
- 以固定用例数量、固定问答轮数或“所有错误都不出现”代替验收。

## 7. 在另一台电脑定位实现

以下均为占位符，不是原电脑的绝对路径：

- `<SKILL_DIR>`：由本机源码构建出的 `generate-test-cases` 技能目录；不要求预先安装。
- `<SOURCE_ROOT>`：用户提供的本项目源码仓库，是实施起点；不假定与构建产物目录相同。
- `<WORK_DIR>`：此次实现工作区。
- `<CATALOG_ROOT>`：测试运行目录的父目录，传入现有创建入口前建立为有效绝对目录。
- `<TEST_RUN_DIR>`：创建入口返回的 `run_directory`，使用该绝对路径，不手工伪造身份。
- `<DOC_DIR>`：本三份文档所在目录。

从提供的源码定位技能、构建和测试入口，按仓库实际方式构建并验证。

已核实的安装包相对路径如下，用于识别对应源码与构建结果；不要求这些文件在构建前已经安装：

| 路径 | 核对内容 |
|---|---|
| `SKILL.md` | 工作流、工件边界、公开调用方式、质量约束 |
| `scripts/test-compiler.mjs` | 运行入口、阶段交接、公开导出 |
| `scripts/schemas/reply.schema.json` | 阶段回复闭合结构 |
| `scripts/schemas/case-drafts.schema.json` | 用例及复核结构 |
| `scripts/schemas/test-obligations.schema.json` | 结果、测试点、观察项结构 |
| `scripts/schemas/ordering-registry.schema.json` | 编译器顺序引用 |
| `scripts/schema-manifest.json` | Schema 集合与摘要，必须由构建同步 |
| `references/*.md` | 证据、澄清、设计、复核、恢复及执行边界政策 |

本次检查的安装包主要包含打包脚本、Schema 与说明，未看到可维护源码工程和测试入口。这不证明源码仓库不存在。接收者应从已提供的源码定位构建方式；不要把文档中的内部符号名误认为磁盘上必然有对应 `src` 文件。

在对应维护源码中修改并沿原构建流程生成产物；不能仅手改打包文件而使源码、Schema 和交付产物不一致。

测试运行沿用现有公开路径：由 `createV4RunDirectory(<CATALOG_ROOT>, "case_document")` 创建身份与运行目录，再执行下列入口取得阶段请求；不要手工编造运行 ID 或复制旧运行目录作为新身份。

```text
node "<SKILL_DIR>/scripts/test-compiler.mjs" "<TEST_RUN_DIR>"
```

stdout 的单个 JSON 回复先按 `reply.schema.json` 校验，再依据状态处理。阶段候选写入已有的 `staging/source-pack.json`、`staging/evidence-claims.json`、`staging/behavior-views.json` 或 `staging/case-drafts.json`，随后重调 Runner。业务回答与材料恢复沿现有受控 helper；正式完成后用 `verifyCaseDocumentDeliveryV4` 检查 `output/current.json` 及其引用。具体调用参数以源码中的现有接口为准。

源码符号中 `Runner` 指接收运行目录并决定阶段推进、提交和交付的入口；`Adapter/helper` 指构造候选和动作的辅助函数；`Schema` 是结构契约；`verifier` 是读取交付并检查绑定和摘要的验证函数。这些都属于现有技能实现，不是需要另外接入的服务。

## 8. 便携验收材料

下列两个样本是独立测试来源，分别创建测试运行，不合并成同一业务规则集。它们只提供回归输入，不得将模块名称、角色或规则硬编码进编译器。样本描述的是待生成用例的业务，不要求实现配置工作台、搭建业务服务或执行界面操作；固定时间和请求结果作为用例设计数据。

### 8.1 本地最小需求样本

以下是专门用于工具回归的合成需求，不是实际 PRD 的新规则。测试时把整段作为提供的需求材料，通过正式来源准备流程建立证据，不手写“已接受”状态。

> 模块：配置管理。角色只有管理员与只读用户。两类角色都可以查看列表和记录详情。只有管理员可以新增配置。新增表单只有名称一个字段，初始为空，必填，允许 1 至 10 个 ASCII 英文字母。点击保存：名称为空时不提交并提示“名称不能为空”；超过 10 个字母时不提交并提示“名称最多10个字母”；合法时新增一条草稿记录并关闭弹窗。保存请求处理中重复点击，最终只生成一条记录。保存失败时保留弹窗和输入内容，允许再次保存。点击取消关闭弹窗，重新打开时名称为空。点击查看显示名称和状态，字段只读。

该样本至少能判定空值、合法边界、超长、授权与未授权、重复提交、失败重试、取消重开、查看只读和新增同一记录的完整路径。非英文字母不属于允许输入域，但样本未规定该情况的具体报错文案；测试不得凭空增加精确文案。

还需实现两个受控变体：

- 删除“保存失败时……”一句，验证缺失必要预期进入业务澄清，不能自动采用常见规则。
- 保持来源不变，故意改坏候选用例的角色、预期或引用，验证对应质量检查和复核能发现问题。

测试夹具应随实现仓库提交，包含源文本、通过真实构造入口准备数据的脚本和独立维护的检查清单。不得依赖原电脑的缓存或运行目录。

### 8.2 本地综合需求样本

以下文本同样是独立、完整的工具回归材料，不是对原 PRD 的摘录或补充。通过现有粘贴需求/本地材料入口准备，不增加新的来源适配器。测试代码应将本节源文本和独立检查清单随仓库提交。

> 模块：配置工作台。角色为管理员、超级管理员、只读用户。所有角色可以筛选和查看；仅管理员、超级管理员可以新增、编辑、复制、下线、启用。
>
> 可编辑字段为名称、开始时间、结束时间。三个字段均必填，名称为 1 至 10 个 ASCII 英文字母。新增时全部为空。时间精度为秒，统一使用 UTC 时间；用例使用明确的当前时刻测试数据，各动作以实际提交时刻判断时间条件。开始时间大于结束时间报错，相等合法。其他非法输入不提交；除下文明确文案外，不要求精确报错文字。
>
> 保存草稿成功后状态为草稿，不受结束时间已过去影响。保存并生效要求结束时间严格晚于当前时间，否则不提交并提示“结束时间必须晚于当前时间”。成功后，开始时间晚于当前时间为待开始，否则为生效中。对已发布且未下线的记录，当前时间早于开始时间为待开始；当前时间大于或等于开始、但小于结束时间为生效中；当前时间大于或等于结束时间为已过期。开始与结束相等时，恰好到达该时刻按已过期处理。草稿和已下线记录不因时间变化自动发布。状态判定采用当前时刻，不约定自动刷新频率。
>
> 待开始、生效中的记录允许下线；二次确认取消不改变记录，确认成功变为已下线。只有已下线记录允许启用：结束时间小于或等于当前时间时提示“无法启用”；结束时间晚于当前时间时二次确认，取消不改变记录，确认成功按开始时间确定待开始或生效中。其他状态不允许对应行操作。下线或启用请求失败时记录保持原状态，提示操作失败并允许重试；请求处理中，同一记录不接受重复行操作。
>
> 所有状态的记录均允许查看、复制；仅草稿允许编辑，且这些操作仍受上述角色权限约束。查看显示全部可编辑字段及状态，均只读。复制先打开带全部可编辑值的新增弹窗，保存成功后才新建记录，原记录不变。编辑打开弹窗时全部可编辑字段清空，保存成功更新原记录，状态依保存按钮及时间规则确定。
>
> 保存成功关闭弹窗。保存失败保留弹窗和全部输入，可重试；请求处理中重复点击只产生一次保存效果，不重复新建记录。取消关闭弹窗，再次打开按对应新增、复制或编辑入口的初始化规则处理，不恢复上次未保存内容。
>
