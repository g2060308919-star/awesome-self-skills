# generate-test-cases 编译器可靠性整改技术方案

本方案在现有四工件架构、证据模型、独立复核和正式交付机制内修复生成可靠性。问题背景和便携需求样本见 [01-context.md](01-context.md)，全部强制验收条款见 [03-spec.md](03-spec.md)。本文中的新接口均为拟实现设计，不能假定当前安装包已经支持。

## 1. 架构决策与边界

保留编译器。保留 `source_pack → evidence_claims → behavior_views → case_drafts` 四个 Agent 编写的语义工件，保留既有澄清、提交、恢复、独立复核和 `output/current.json` 发布路径。

本次只补齐阶段交接和构造接口，并清理不再需要的技能多版本分派。不得引入第五个 Agent 编写的语义工件、替代流程引擎、新证据等级或新的执行系统。

新增的 `case_context` 是编译器生成的只读回复数据，不是 Agent 写入的新语义工件，不是正式交付，也不能用它证明独立复核已完成。

## 2. 先定位源码，再建立故障复现

使用背景文档的目录占位符。从用户提供的源码开始，定位技能入口、构建脚本、Schema 生成方式和测试命令；按仓库实际方式构建并验证。若仓库有 `.codegraph/`，按仓库规则先使用 CodeGraph 定位；没有则使用普通文本搜索。

当前发布包提供了以下内部符号线索；它们用于定位，文件布局与行号不是跨机器契约：

| 现有符号或文件 | 实施用途 |
|---|---|
| `advanceStrictV4Operation`、`artifactRequest`、`revisionReply2` | 阶段调度、写入候选请求和校验失败回复 |
| `compileCaseDocumentRevisionV4` | 现有完整用例编译与质量门禁 |
| `compileBusinessOutcomesV4` | 唯一正式结果、测试点和观察项身份计算 |
| `compileSemanticCaseDocumentV4` | 保持既有正式 CASE 语义身份计算 |
| `completeSystem`、`deriveV4SystemContext`、`deriveV4PreCaseSystemContext` | 来源获取状态与业务证据上下文构造；定位当前四工件参数检查与可复用的前置计算 |
| `compilePreCaseArtifactsV4` | 来源、证据、范围与设计前澄清的既有前置门禁 |
| `compileOrderingRegistry` | 编译器管理的流程、动作和依赖引用 |
| `constructV4Action` | 澄清及其他已有动作的受控构造 |
| `constructIndependentReviewCompletionV4` | 独立复核完成记录的受控构造 |
| `scripts/schemas/*.schema.json` | 对外数据契约 |
| `scripts/schema-manifest.json` | 与打包产物一致的 Schema 集合和摘要 |

建立一个合法的最小来源、证据与行为设计，使用正式入口推进到 `case_drafts` 请求。失败测试应证明：请求未提供该阶段必须引用的测试点。不得用错误业务材料导致的拒绝冒充此次接口缺陷。

同时保留正常材料、必要业务缺口、非法引用和失败恢复测试。先有失败断言，再修改实现。测试命令以接收仓库实际脚本为准；不得把不存在的 npm 命令写成已运行。

## 3. 抽取共享的用例编写上下文计算

### 3.1 消除空用例探测的循环依赖

现状通过空 `case_drafts` 调用完整编译过程探测行为设计，最终仍要求 Agent 提交尚无测试点引用的用例。

当前 `deriveV4SystemContext` 对参数有“恰好四个工件”的检查，但其实际计算使用来源、证据和材料获取状态。只把行为探测调用改成三个工件会继续失败；补一个假的空 `case_drafts` 也没有消除依赖。

在现有模块内抽取不依赖用例的上下文计算，复用 `deriveV4PreCaseSystemContext`、行为证据和顺序依据的现有派生逻辑，并保留材料凭证及已接受澄清状态的校验。完整四工件编译入口保留原校验与职责，内部调用同一前置计算，不新增一套推导算法。

随后抽取共享函数，建议名称 `compileCaseAuthoringContext`，接收来源、证据、行为工件及已验证系统上下文。该名称是新内部函数，不要求移动模块目录。职责顺序如下：

1. 验证当前来源、证据、范围及已接受澄清状态；保留现有前置门禁。
2. 验证行为工件结构、证据绑定、设计责任与处理结论。
3. 调用现有 `compileBusinessOutcomesV4`，不复制或改写身份算法。
4. 调用现有顺序注册表构造逻辑；不得因缺少顺序依据而按标题编造顺序。
5. 返回事实、范围、结果、测试点、观察与顺序等编写数据，或返回现有类型的具体失败结果。运行身份及依据摘要由 Runner 在该数据之外封装为 `case_context`；不得将运行路径或身份混入业务结果、正式 CASE 的语义计算。

行为阶段与完整用例编译阶段调用同一实现。内部返回结果须由 Runner 沿既有映射生成合法回复；内部 `kind`、`status` 或错误对象不直接作为顶层协议输出。该函数不接受虚假的空用例来跳过前置条件，也不运行依赖真实用例内容的覆盖闭合、独立复核和正式发布。

完整用例编译必须继续检查用例结构、语义状态、引用、覆盖、风险审阅、独立复核和交付一致性。不能因前置上下文已计算而省略最终校验。

### 3.2 行为阶段提交顺序

在既有锁和事务边界内：校验候选行为工件 → 成功计算上下文 → 按原机制接受该工件 → 返回与实际已接受内容绑定的用例编写请求。

若校验或上下文计算失败，不接受该行为工件，不发出可写正式用例的有效上下文。不得吞掉 `fatal`、未知状态或非用例阶段的错误后继续推进。

实现时保持现有提交机制，不新建另一套提交日志。进程中断后由现有恢复入口重放或重算，不能把内存中计算成功等同于已经提交。

## 4. 用例阶段回复契约

### 4.1 新增只读字段

在 `reply.schema.json` 中为允许编写或修正 `case_drafts` 的回复定义 `case_context`。复核请求若允许修正用例内容，也必须使接收者取得当前有效上下文；纯提交复核结论沿用原 `review_request` 约束。

`case_context` 采用闭合结构，下表字段全部必填，数组字段不得用 `null` 替代；可定义为新的 `scripts/schemas/case-context.schema.json`，并由正式构建同步注册。新增 Schema 不是新增语义工件。字段如下：

| 字段 | 类型与来源 |
|---|---|
| `run_id` | 字符串，复用现有运行 ID 格式与身份 |
| `source_revision` | 非负整数，用例请求要求的任务修订；与已接受上游前缀一致 |
| `basis` | 闭合对象，包含 `source_pack_digest`、`evidence_claims_digest`、`behavior_views_digest` |
| `facts` | 数组，已验证 `evidence_claims.fact_ledger` 的完整事实记录，复用其现有结构 |
| `fact_modules` | 数组，原结果编译器输出的事实到所属模块映射，不由调用方猜测 |
| `modules` | 数组，已验证 `scope_manifest.modules` 的完整模块记录，复用其现有结构 |
| `outcomes` | 数组，现有结果编译器返回的完整结果数组 |
| `formal_test_points` | 数组，现有结果编译器返回的完整测试点数组 |
| `supporting_observations` | 数组，现有结果编译器返回的完整支持观察数组 |
| `ordering_registry` | 闭合对象，复用既有 `business_flows`、`page_actions`、`dependency_rules` 注册表 |
| `context_digest` | 除自身字段外，整个上下文按现有规范 JSON 序列化后的 SHA-256 摘要 |

本方案中新增摘要字段统一为 `sha256:<64位小写十六进制>`；内部使用既有摘要函数并做格式转换，不改写已有字段的摘要约定。`basis` 绑定规范工件内容，不是文件路径或任意文本文件的哈希。

测试点通过 `outcome_id` 关联结果，结果通过 `fact_id` 关联 `facts`，所属模块通过编译器的 `fact_modules` 关联 `modules`；每条引用必须可唯一解析。验收角色来自对应 outcome 的 `acceptance_role`；正式编译继续复用现有 `pointsWithRoles`，不另造角色判定规则。数组的规范顺序复用现有实现，不改变语义上有序的步骤和事件数组。

无适用测试点的合法场景沿用原有判定与交付语义；不允许为了推进而清空原本存在的测试点。

### 4.2 什么时候返回

- `behavior_views` 成功接受后，返回请求 `case_drafts` 的回复及完整上下文。
- 中断恢复后仍在等待用例时，重算并返回同一已接受内容的上下文，不依赖此前终端输出。
- 修正尚未接受的用例时，返回其当前依据对应的上下文。
- 上游依据被合法修正后，返回新依据的上下文；旧上下文不能继续提交。
- 上下文尚不能合法生成时，返回真正出错的现有阶段与诊断，不返回空壳或伪造编号。

不得静默截断或采样测试点数组。普通工具显示截断不改变 JSON 协议完整性；调用方需要读取完整回复。此次不设计分页协议。

### 4.3 用例候选绑定与最终重验

在现有 `case_drafts` 根对象增加必填机械字段 `case_context_digest`，格式同 `context_digest`，由构造入口复制当前有效上下文摘要；正式 CaseSpec 的业务字段不变。该字段用于候选依据校验，不加入正式 CASE 的身份投影，也不单独决定独立复核是否有效。

Runner 接收候选时，在既有提交锁内依次处理：

1. 检查工件结构。摘要缺失或格式错误沿用普通 Schema 诊断，不伪装成上下文过期。
2. 从当前已接受上游前缀及有效材料/澄清状态重算上下文；前置不成立时返回真正出错的阶段与既有恢复动作，不发出有效用例上下文。
3. 核对候选的任务修订与 `case_context_digest`。格式合法但摘要不匹配时，返回 `need_revision / case_drafts / CASE_CONTEXT_STALE` 及当前有效上下文。其他已有修订错误仍保留其诊断，不吞并为新错误码。
4. 上下文匹配后继续检查测试点、观察、顺序、步骤及后续质量门禁。错误引用返回对应的现有工件诊断，不要求无意义地刷新上下文。

以上失败均不接受该用例候选、不改写历史、不发布新结果。更新依据后需要重查受影响语义，不能仅替换摘要来掩盖内容失效。只更新独立复核记录且上游依据未变时，保留原上下文摘要；复核目标及内容变化仍按既有规则验证。

helper 必须将所收上下文与只读重算的当前上下文完整对照；仅验证“内容与所附摘要自洽”不足以确认有效性。篡改内容，即使重新计算了所附摘要，仍须拒绝。使用拟新增诊断 `CASE_CONTEXT_INVALID`；当前回复不允许目标构造动作时使用 `STAGE_NOT_WRITABLE`。这些是构造/校验诊断，不新增 Runner 顶层状态。

## 5. 统一数据构造入口

### 5.1 新入口与现有入口的关系

在现有安装包公开导出一个拟新增 helper：

```text
prepareStageArtifact(runDirectory, validatedReply, semanticInput)
  -> { status: "prepared", stage, artifact }
  |  { status: "invalid", diagnostics }
```

这是拟新增的异步 Adapter helper，返回上述结果的 Promise，不是 Runner 阶段回复。结果结构需要闭合 Schema 和测试；失败的 `diagnostics` 为非空数组，复用现有诊断结构，至少包含 `code`、`path`、`message`，不返回半成品 `artifact`。不能把 `prepared` 当作正式接受。函数只读当前运行并构造内存候选，不写已接受目录、不推进阶段、不修改 `output/current.json`。调用方将成功候选写入既有 staging 文件后，仍调用正式 Runner。

- `runDirectory` 是当前机器合法的绝对运行目录。
- `validatedReply` 必须先通过正式回复 Schema；helper 还需核对当前运行状态，不能信任调用者声称“已校验”。
- `semanticInput` 为闭合对象 `{stage, payload}`，用于当前回复明确允许的 `write_stage_artifact` 或 `revise_artifact`；`stage` 必须与阶段及 Schema 匹配。材料恢复、业务回答驱动的 Source Pack 追加、取消等继续走现有受控动作路径，不强行改接到此 helper。
- `payload` 沿用对应阶段现有结构，但省略由程序补入的字段。所有阶段省略 `schema_version`、`source_revision`；`source_pack` 另省略 `run_instance_id`；`case_drafts` 另省略 `case_context_digest`。这些字段由当前合法请求与运行身份确定，不按调用次数增加修订。其余已准备好的来源、受控事件和业务成员保持原结构。调用方提供这些保留字段或未知字段时明确拒绝，不静默覆盖或丢弃。

新入口是现有合法流程的便捷构造层，不替代下面这些受控接口：

- 来源字节、签名链接清理、摘要与审阅单位仍由 `prepareV4Source` 及现有来源校验完成；不能接受模型伪造的来源摘要。
- 材料获取、用户回答与控制动作仍通过现有受控 helper 构造，校验当前 presentation 和目标绑定。
- 独立复核仍通过 `constructIndependentReviewCompletionV4` 提交真实的评估结果。
- 正式 Runner 继续作为唯一接受和交付权威。helper 核对状态使用现有只读加载和校验路径，不能为了检查而调用可能推进提交的 Runner。读取期间发生上游变化时允许拒绝并重取回复，最终仍由 Runner 锁内重验防止竞态。

### 5.2 各阶段输入处理

| 阶段 | payload 保留内容 | 程序处理 |
|---|---|---|
| `source_pack` | 由现有来源准备流程形成的安全来源、定位、审阅及受控事件 | 按原 Schema 补入当前修订等允许的头部；调用原来源校验；不重新解释原始材料 |
| `evidence_claims` | 事实、Claim、范围、缺口和接受角色等原语义成员 | 补入头部；校验引用、字段类型及既有来源支持声明；拓扑计算仍调用原受控构造入口，不把结构校验当作自然语言判真 |
| `behavior_views` | 原行为视图、交互、责任记录等语义成员 | 补入头部；检查引用及设计完整性；不自动删除未处理责任 |
| `case_drafts` | 用例业务内容与符合现有协议的独立复核记录（pending 或 completed） | 补入头部和上下文摘要；检查候选局部 ID；核对编译器提供的引用与步骤绑定 |

头部字段以各阶段现有 Schema 为准；运行身份用于核对，不得擅自在没有该字段的工件中增加 `run_id`。本次明确新增的工件字段仅为上述 `case_context_digest`。

`schema_version` 等当前固定元数据若仍为原协议所必需，由程序填写；不得让 Agent 选择版本。来源修订、已接受事件序号和摘要不允许调用方随意覆盖。

Claim、Fact、View、步骤等由 Agent 定义的语义局部标识仍按现有规范使用；helper 检查其唯一性和引用一致性。本次不重写这些实体的核心身份算法。所谓“机械字段程序化”不意味着程序替 Agent 决定事实如何拆分、条件如何组合或预期是什么。

### 5.3 用例 ID 与引用选择

候选继续沿用当前 Schema 的 `case_id` 输入，由 Agent 提供批内唯一的局部标识；helper 检查非空、唯一性及引用一致性，不引入 `case_key` 或第二套编号算法。它不是调用方必须复刻的内部测试点哈希。

正式 CASE 身份继续由 `compileSemanticCaseDocumentV4` 按现有语义投影计算。不得改用运行 ID、候选局部编号、时间或随机数产生正式 CASE 身份。既有 OUT、TP、OBS、FLOW、ACTION、DEP 身份算法同样保持不变。

已有 `step_id`、`oracle_id` 等用例局部键保留，helper 检查唯一性及 `observe_after_step_id` 是否存在；不会按相似文字猜测关联。涉及正式 CASE 身份的复核记录继续使用现有编译结果和受控复核入口绑定，不以候选局部标识替代正式编号。

Agent 从 `case_context` 选择 `primary_test_point_id`、支持观察及允许的顺序引用；不自算它们。没有来源支持的顺序仍用原协议允许的 `null`，不添加排名、依赖或新流程。上下文中的完整测试点集合不代表每一点均可无条件计为正式覆盖，适用性和处置仍按现有证据及设计责任规则判定。

用例内容变化时，按原语义身份与内容摘要规则处理；原复核失效检查必须保留，不能以候选局部标识未变为由复用旧复核。

### 5.4 可以与不可以自动修复的内容

允许：填写受控头部、按既有集合规则规范化无序集合、计算机械摘要、准确绑定已有引用、提示具体缺失字段。

禁止：猜测默认值、生成未知预期、升级证据等级、把未知标为不适用、丢弃必测责任、按名称相似度替换事实、删除错误候选以凑齐通过结果、伪造用户确认或独立审阅。

## 6. 单一数据契约和发布一致性

以源码中的一份当前协议定义为数据结构权威。构造入口与 Runner 的重叠检查必须调用同一校验实现；helper 不提前要求独立复核的 completed 结论、完整覆盖或后续阶段数据，Runner 保留完整门禁。当前用例 Schema 要求的 `independent_review` 不能省略：首次提交保留合法 pending 对象、真实 reviewer 身份和先读来源得到的 `source_first_targets`；完成结论仍由原受控 helper 绑定。不得以消除循环依赖为由删除 pending 结构或伪造目标。外置 JSON Schema 和打包脚本中的嵌入定义由同一构建生成或在构建时严格比对。

同步范围至少包括：回复、用例候选、新上下文、构造 helper 结果结构、Schema 注册清单和摘要，以及技能说明中的调用范例。不能只改外置 JSON 或只改打包文件。

当前安装包入口和必要的公开 helper 名称保持稳定。已有名称含 `V4` 不构成多版本兼容需求，无需为去掉字样而扩散重命名。

以实际仓库构建工具为准，不引入新的依赖或构建框架作为前提。发布验收必须从重建后的安装包运行，不能只证明源码测试通过。

## 7. 移除技能多版本兼容

实施前列出兼容入口、升级/迁移分支、历史 Schema 分支、文档和相关测试的依赖清单。逐项区分旧技能支持与当前任务完整性检查。

删除或停用：

- 按历史 schema/compiler 配对分派到不同实现的运行路径。
- 面向旧工件的适配、降级、回退与迁移流程。
- `version_upgrade` 创建理由及 `VERSION_UPGRADE_REQUIRED` 式升级引导。
- 仅为上述能力存在的旧 Schema 分支、迁移索引和文档操作步骤。

保留：

- 当前任务修订、事件顺序、当前问题绑定、证据摘要和复核摘要。
- 当前协议的构建完整性和外部 provider 契约校验。
- `resume_cancelled`、`NEW_RUN_REQUIRED` 对应的来源/范围变更和语义重开等现有机制。来源字节或实质范围变化仍创建关联新运行；取消恢复也创建新运行，不恢复向取消日志写入。
- 现有交付和下游引用所需要的字段及语义。

对不符合当前结构的输入给出明确拒绝及安全处理说明，不尝试解释成旧版本或自动新建升级运行。原历史文件保留原样；不要求本次实现提供历史阅读或迁移服务。

本次在不改变上述核心协议形状的前提下保留必要的固定元数据。不得借“不要版本”之名全局删除字段，从而破坏来源凭证、当前任务恢复或下游读取。

## 8. 错误分类与恢复

沿用 Runner 既有状态：`need_artifact`、`need_user_answers`、`need_revision`、`fatal`、`finished`、`cancelled`。`STAGE_ARTIFACT_REQUIRED` 是正常请求候选工件，不应在用户界面被解释成故障。

| 情况 | 处理与恢复 |
|---|---|
| 正常等待某个阶段工件 | 保留 `need_revision` 与 `STAGE_ARTIFACT_REQUIRED` 的现有组合，返回 stage、Schema、当前上下文与已有写入动作；Agent 自动继续 |
| 结构/引用错误 | `need_revision` 定位工件和字段；仅修未接受候选后重试 |
| 业务预期未知 | `need_user_answers`；保持当前问题及已接受回答，不让技术错误混入问题列表 |
| 来源材料未获取 | `need_artifact`；沿用稳定资源与材料校验恢复；合法可复用材料不要求重复获取 |
| 旧候选/旧上下文 | 拒绝写入，返回当前依据；重新设计受影响内容后再提交 |
| 内部异常/完整性失败 | 明确 `fatal` 或现有不可恢复诊断；保留现场，禁止伪造成功或无限重试 |
| 用户取消 | 沿用现有取消与显式恢复规则 |

Runner 的失败回复应说明原因、出错对象、当前是否发生提交、下一项合法动作和恢复位置；没有安全恢复动作时明确说明，不能虚构可执行动作。保持现有字段表达，只有无法表达时才在当前闭合 Schema 内增加最小必要信息，不另建错误处理系统。

重复调用、重复提交相同回答及进程中断不得造成重复决定、重复用例或旧结果覆盖新结果。并发候选通过原锁与摘要机制串行验证，不通过“最后写入覆盖”处理冲突。

无进展重试属于现有 Agent/Adapter 工作流控制：同一规范化阶段和根因允许三次修正，第四次相同无进展结果报告 `PIPELINE_NO_PROGRESS`。它不是新增 Runner 状态、编译器 `fatal` 或业务 Blocked。不得用行政修订或自动重开运行绕过上限，也不新建全局重试服务。暂时性外部故障沿既有恢复机制处理，不能无界循环。

## 9. 质量与验收设计

### 9.1 两类回归必须分开

**流程回归**检查合法数据如何到达正式交付：正常路径、澄清、获取材料、恢复、修正和导出。

**质量回归**检查错误内容是否被识别：引用断裂、没有来源的预期、遗漏需求、错误角色/状态组合、步骤预期错位、对象不连续、失效复核等。

结构和引用错误由确定性校验处理；业务语义是否符合自然语言 PRD 由来源对照与独立复核负责。测试不能声称 JSON Schema 能自动理解所有自然语言需求。

### 9.2 独立基准与双向追溯

基准需求文本与预期检查清单独立维护，不能从生成结果反推“应该覆盖什么”。至少检查：每条有效源规则有结果/用例或真实缺口处置；每条用例预期都能回到有效来源；未提取的源规则也能在独立复核中被发现。

固定场景的语义反例可以有确定性断言；本地综合样本的完整生成验收仍需真正独立上下文复核，不能因来源是合成文本就跳过质量流程。自动化协议测试可以模拟复核消息结构，但必须标注为测试夹具，不能冒充真实独立审阅，也不能作为真实交付的审查记录。

### 9.3 验收层次

1. 单元/契约：上下文结构、摘要、引用、构造结果与错误分类。
2. 集成：真实 Runner 推进四工件、恢复与修正；不手写已接受数据。
3. 质量反例：逐类故意破坏候选，验证对应门禁/独立复核发现问题。
4. 打包验收：从生成后的安装包调用实际公开入口，完成生成并用原交付 verifier 校验。
5. 本地综合样本：使用背景文档第 8.2 节完整文本，经真实生成、独立复核和导出流程验收。来源在文档中完整提供，不调用外部业务系统。外部读取接口用本地测试替身验证契约，不将其称为真实服务验收。

## 10. 实施任务和检查顺序

| 任务 | 修改范围 | 验证与退出条件 |
|---|---|---|
| T01 建立基线 | 测试夹具与仓库实际测试入口 | 最小合法输入复现“无用例上下文”；记录失败断言及现有门禁基线 |
| T02 修复阶段交接 | 现有调度与编译模块、上下文和回复 Schema | 接受行为工件前通过前置校验；无用例也可返回完整上下文；恢复返回等价内容 |
| T03 统一构造 | 公共 helper、共享校验、用例 Schema、导出入口 | 合法语义输入得到合法候选；篡改/失效上下文与错误引用被拒绝；不擅改业务语义 |
| T04 清理版本路径 | 当前协议选择、迁移专用代码、历史 Schema 分支、说明 | 无技能升级迁移运行入口；当前任务恢复、凭证和下游契约仍通过 |
| T05 验证恢复与质量 | 既有事务/错误处理涉及的最小代码及回归测试 | 中断、重复、并发、失效复核、业务缺口及反例按 spec 正确处理 |
| T06 重建与本地完整验收 | 构建、安装包、文档与本地综合样本 | 打包产物契约一致；样本生成及正式交付验真通过；真实独立复核完成；不依赖业务 MCP |

对需修复的行为采用失败测试 → 最小实现 → 针对性回归；对已经正确、仅要求保持的机制，补充或复用保护测试即可，不人为制造失败再改实现。发现新的独立根因时增加相应测试；不得只改错误文案或提高重试次数。

源码文件名和测试命令须在 T01 记录为实际值，再据此实施；本方案不凭打包注释虚构源码路径。不能因发布包只有一个大文件就把局部整改扩大成全量模块重写。
