# 检查点、探索与结果模型

## 权威标准

`expected[].text` 是唯一通过标准。页面显示近义词不能自行放宽；例如期望“评分”而实际只有“用户评分”，若精确语义不满足就记录未通过和实际文字。运行后的新标准只能进入新用例和新 Run。

每个 oracle 映射为 `<case_id>/<step_id>/<oracle_id>`，独立保存事实与证据状态。不得因后续阻塞覆盖已完成项。

## 固定四态

| 内部值 | 展示 | 使用条件 |
|---|---|---|
| `passed` | 通过 | 明确事实支持满足原文 |
| `failed` | 未通过 | 明确事实支持不满足原文 |
| `undetermined` | 无法确定 | 已尝试但事实不足 |
| `not_executed` | 未执行 | 整条用例在正式执行前明确排除 |

缺账号、环境/工具阻塞、没有动态样本或执行中断均不是 `not_executed`，而是 `undetermined`。`已就绪`、`待用户准备`、`明确无法提供` 是权限资源状态，不是新的产品结果。等待期间尚未执行的检查点保留 pending/null，阶段报告的 case 聚合仍为 `undetermined`；用户明确无法提供或决定本轮不再等待时，真正受影响检查点写入具体 `undetermined` 原因，不得记为产品 `failed`、`excluded` 或 `not_executed`。已发生的失败优先级不被权限原因遮盖。

聚合顺序固定：任一检查点 failed → case failed；否则任一必需检查点 undetermined → undetermined；否则全部必需检查点 passed → passed；否则若整条 case 预先排除 → not_executed；其余 → undetermined。证据、截图、代理、清理和 Run 状态独立，不能改写产品结果。

## 覆盖完整性与 Mock 有效投影

新 Run 的结果字段非空不等于执行完整。每个检查点必须先通过 `coverage_plan` 建立全部必要范围和依赖；开始时引用新鲜 `coverage_context`；终结时引用覆盖所有必要站点/步骤的 `checkpoint_close` 审查；最终 `coverage_review.final` 逐项核对全部原检查点。A→B→A 的返回任务、独立可推进工作、未解除协作和实际依赖不能被“当前页面做完了”或自由文本原因跳过。阶段报告可以显示 pending/null 的待继续范围，但不能反写终结结果。

`data_gap` 是真实环境事实，不是 Mock 通过。用户拒绝 Mock 时仍可记录数据缺口并据实得到 `undetermined`。用户允许后，候选须明确 `assertion_domain` 与原断言依据，只有 frontend 可记录 Mock passed，并以同尝试/检查点的 `page_observation_refs` 证明页面消费。只有同一原预期、合法数据缺口、完整前端执行证据及已完成候选收尾才能形成有效 Mock 投影：

1. 原始真实 `failed` 永远优先并保留；Mock 不能覆盖。
2. 有效 Mock `failed` 表示真实前端在该合成输入下不符合原预期，优先于通过。
3. 真实 `passed` 保留为纯真实通过。
4. 真实 `undetermined` 只有缺口和补测范围精确一致、没有其他必要阻塞时，才可投影为带来源的 passed/failed。
5. 配置、代理、状态、清理或证据关联错误不是产品失败；真实后端持久化、真实数据创建等后端专属断言继续 `undetermined`。

原 `cases[].checkpoints` 和 `cases[].result` 始终保存原始真实结果，不被 Mock 回写。报告模型一次性计算有效投影，仍只输出四态、每条输入用例一行、原顺序不变。含 Mock 的原因醒目标注“Mock 前端补测”，概览分别显示纯真实通过和含 Mock 通过；详情同时显示原始真实结果、真实数据缺口、补测页面/请求事实和“不证明真实后端”的边界。HTML 与 `chatTableMarkdown` 必须共享这个唯一 rows/counts 模型。

原因必须是语义化中文事实，说明期望、实际、位置和影响；不能只写错误码、`false`、`timeout` 或“与预期不符”。通过也要写观察事实。

权限准备声明只说明账号资源状态。执行前核验的是实际账号、非生产环境、已登记 Target、存储上下文和必要切换，不要求被测权限行为先成功。上下文正确而业务行为不符合原 `expected[].text` 时正常记录 `failed`；错账号、环境不明或切换未完成时先修复或协作，不把上下文问题伪装成产品失败。

协作请求是进度状态，不是产品结果。开放协作覆盖的检查点保持未完成；只暂停真正依赖该事项的范围，独立工作继续。用户明确无法协助、停止部分等待或停止全轮后，只对精确影响范围按现有四态收尾，保留既有通过和失败。

最终写入 `undetermined` 时，必须内联合法 `exploration_summary` 或用 `exploration_ref` 引用先前 blocker 摘要。摘要包含精确检查点、具体缺口、已知事实、真实尝试和结果；没有尝试时使用 `not_attempted_reason`；始终说明 `cannot_continue_reason`。完整字段不能自动证明探索充分，也不能绕过开放协作或未开始检查点的终结条件。

## 准备调整、表单与补充观察

执行前按原检查点登记 `checkpoint_semantics`：前端、真实后台或真实权限断言；固定、普通准备或直接被测条件。不能因页面规则更严格就改写原条件。`preparation_adjustment` 只适用于有事实依据的普通准备值，记录原值、替代值、目标不变理由、支持范围及实际准备验证；出现具体数字并不自动使普通基线变为核心条件。

上传断言要求 750×360、100,000 字节或允许 4,000,000 字节，而页面只接受 750×600、≤200,000 字节时，实际拒绝应保留 `failed`。独立 ID 检查仅用图片作普通基线时，可记录调整后使用 750×600、100,000 字节完成真实保存与 UI 回读，按原 ID 断言得到带“准备数据已调整”属性的真实结果。同一 case 同时包含两项时仍聚合 failed，每条原输入只显示一行。

核心值、指定资产、身份、边界或明确必需步骤不能替换后提升原结果。不确定等价性时只暂停受影响范围；替代测试通过 `supplementary_attempt` 保存观察，原已终结结果不覆写。后来的替代图片成功或 Mock 成功都不能消除原真实失败。

`form_interaction` 区分工具填值、控件确认和可见回读；文件选择、上传和业务保存分别记录。未完成组件确认的输入属于测试操作缺口，不能据此认定产品拒绝合法输入；操作正确完成后仍不符合原预期才可判失败。没有保存/UI 回读事实不能把弹窗关闭或 Mock 返回 ID 当真实保存。

来源为纯真实/含模拟/未知以及准备调整范围，独立于四态。真实后台持久化、真实访问控制或状态流转要求仍按实际后台事实判断；只有模拟成功时不能宣称这些要求通过。日志、HTML、对话表和统计使用同一投影，详情保留原结果、调整理由、补充尝试、Mock 影响和证据缺口。

发生 `control_effect` 时同一投影标明“含模拟或控制影响”，展示实际匹配阶段、范围和影响说明；单纯配置不能制造来源证据，响应阶段控制不能冒充请求前隔离。`capture_scope` 将页面与请求详情分开保留：最新请求详情采集失败不能被页面成功截图遮盖，证据不完整不改变原产品结果。

清理与来源也独立：进程退出、锁释放、页面安全退出、真实响应恢复分别显示实测事实；CDP 断连不能证明 Fetch 仍有效，必须标为隔离未知并停止业务动作。缺少恢复证据不重写之前产品结果，但报告须明确未验证范围。

## 报告

只持久化 `report.html`，不生成 `report.md` 或等价完整 Markdown。HTML 与命令返回的 `chatTableMarkdown` 由同一次快照和日志读取建立的唯一 rows/counts 模型派生；后者只供对话发送，不落盘。旧 workflow 和旧 Run 在业务操作前明确拒绝；不生成、迁移或修复旧报告。渲染器不重新判定或补造事实；缺失信息显示“未记录”。

HTML 固定六部分：标题、概览、测试环境、需求覆盖与验收、测试数据与清理、结论边界和后续行动。概览按全部输入用例计算四态、通过率、失败率和扣除全局用户等待后的执行耗时；时间事实不足显示“无法准确计算”。阶段报告醒目标明未完成、记录截止和待协作事项，pending 检查点仍是待继续状态。

总表每页最多 20 条；短编号只按不可变输入顺序生成并用于展示。查看弹窗保留原始 case ID、原用例/预期、对应权限、真实执行记录、结果原因、探索事实和全部关联关键截图。未记录动作不能复制原步骤后冒充实际执行。长 ID、长中文和图片不能遮挡关闭操作；固定脚本只负责分页、打开/关闭和焦点恢复。

HTML 主阅读层只展示语义化内容。关键执行记录转换为中文时间线，代理、清理、一致性和证据转换为“项目、实际情况、结论”；不得把事件对象、内部事件名、机器枚举、布尔值、空值或 JSON 代码块直接输出到 HTML。原始序号、哈希、Target ID 和完整载荷继续保存在 `execution-log.json`，HTML 只保留用例 ID、Run ID 和业务记录 ID 等理解、定位结果所必需的标识。无法生成语义摘要的记录显示统一的未识别说明，不泄漏原始载荷。

总表表头精确为：

```text
ID | 模块 | 测试场景 | 测试结果 | 成功/失败的原因
```

每条输入用例按原始顺序恰好出现一次，使用与 HTML 一致的展示短编号和四种中文结果；详情保留原始 case ID。不得增加原因分类列。截图失败只能写在证据状态/原因中，不能改变已有产品判断。

## 对话交付

“最终”指本轮测试明确结束，不是每次助手回复结束。确认、求助、等待、暂停和中断时不展示报告链接或全表；内部仍生成并验证阶段报告。用户明确索要阶段结果才允许 `deliver --stage requested`，标记未完成。正常对外调用 `deliver`：未结束时返回 `deliverable: false`；完成时返回校验报告及同源表格。明确提前结束须沿用原协作事件合法收尾并标明未完成范围，不得因工具失败或用户暂未回复擅自结束。

最终对话中的四态统计和五列表格必须使用已校验 `deliver` 命令返回的 `counts` 与 `chatTableMarkdown`（内部复用 `report`），不得依据记忆重新汇总或判定。对话表头、展示 ID、模块、场景、结果、原因和顺序与 HTML 共享模型完全一致；每条输入用例恰好一行，即使用例很多也不能省略通过项。报告链接不能替代对话内全量表格。报告生成或一致性校验失败时，不得宣称 Run 完成或拼造表格。

最终顺序为：Run 根目录和四态数量；完整五列表格；未通过、无法确定与关键截图缺口；代理验证与自动清理结果（未使用时写“本次未使用代理”）；单一 `report.html` 链接和一致性结果。CLI 的 `reportPath` 和 `htmlReportPath` 均指向 `report.html`，`reportFormat` 固定为 `html-only-v1`。密码及其他认证秘密不得出现在最终回复。
